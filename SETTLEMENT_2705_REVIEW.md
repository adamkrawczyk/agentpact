## 2. New issues introduced in revision (P0/P1/P2)

- **P1 — `sellerTarget` is enforced on-chain, but the discover-path visibility rule for targeted intents is still underspecified against the current auth model.**
  **Evidence:** The revised plan says `sellerTarget` is enforced in `claimIntent()` and `acceptIntentB()` and that `GET /api/intents/discover` should hide targeted intents from anonymous callers while showing matching targeted intents to the requesting agent ([plan](/home/adam/obsidian-vault/projects/agentpact/2026-05-27-v2-settlement-protocol-plan.md:167), [plan](/home/adam/obsidian-vault/projects/agentpact/2026-05-27-v2-settlement-protocol-plan.md:168), [plan](/home/adam/obsidian-vault/projects/agentpact/2026-05-27-v2-settlement-protocol-plan.md:169), [plan](/home/adam/obsidian-vault/projects/agentpact/2026-05-27-v2-settlement-protocol-plan.md:171)). The same revision also makes `/api/intents/discover` a public route via the auth allowlist change ([plan](/home/adam/obsidian-vault/projects/agentpact/2026-05-27-v2-settlement-protocol-plan.md:327), [plan](/home/adam/obsidian-vault/projects/agentpact/2026-05-27-v2-settlement-protocol-plan.md:343), [plan](/home/adam/obsidian-vault/projects/agentpact/2026-05-27-v2-settlement-protocol-plan.md:345)). In the live API, public GET routes return before `app.authenticate()` runs, so `request.agentId` is never populated on those requests ([index.ts](/home/adam/agentpact/apps/api/src/index.ts:1246), [index.ts](/home/adam/agentpact/apps/api/src/index.ts:1263), [index.ts](/home/adam/agentpact/apps/api/src/index.ts:1304), [auth.ts](/home/adam/agentpact/apps/api/src/auth.ts:72), [auth.ts](/home/adam/agentpact/apps/api/src/auth.ts:101)).
  **Risk:** The core `sellerTarget` authorization rule is now specified, but the discovery rule for targeted intents cannot work as written unless the route can sometimes know the caller’s agent identity. Without an explicit optional-auth path, targeted intents either stay invisible to everyone except direct `GET /api/intents/:id`, or the route must stop being truly public.
  **Suggested fix:** Specify one of two designs in the plan: `discover` is anonymous-only and returns open intents only, or `discover` supports optional API-key auth with a separate lightweight auth path that populates `request.agentId` without rejecting anonymous callers.

- **P1 — The new MCP pubkey-registration tool shape cannot satisfy the API flow defined in § 2.6.**
  **Evidence:** The registration flow requires a nonce-bearing challenge and then a POST body containing both `challenge_nonce` and `signature` ([plan](/home/adam/obsidian-vault/projects/agentpact/2026-05-27-v2-settlement-protocol-plan.md:201), [plan](/home/adam/obsidian-vault/projects/agentpact/2026-05-27-v2-settlement-protocol-plan.md:210), [plan](/home/adam/obsidian-vault/projects/agentpact/2026-05-27-v2-settlement-protocol-plan.md:215)). But the revised MCP surface only defines `agentpact.register_encryption_pubkey(signature)` ([plan](/home/adam/obsidian-vault/projects/agentpact/2026-05-27-v2-settlement-protocol-plan.md:352), [plan](/home/adam/obsidian-vault/projects/agentpact/2026-05-27-v2-settlement-protocol-plan.md:361)). The premortem says the SDK will auto-handle the 412 bootstrap round-trip ([plan](/home/adam/obsidian-vault/projects/agentpact/2026-05-27-v2-settlement-protocol-plan.md:481)), but the MCP section does not give equivalent challenge acquisition or retry semantics.
  **Risk:** An MCP client cannot complete first-time bootstrap from the documented tool shape alone. The tool surface is missing either the challenge nonce input or a contract that `create_intent` internally performs the 412 challenge/retry choreography.
  **Suggested fix:** Either change the MCP tool contract to accept `challenge_nonce` plus `signature`, or state that `agentpact.create_intent` handles the 412 exchange internally and `register_encryption_pubkey` is removed from the public MCP surface.
